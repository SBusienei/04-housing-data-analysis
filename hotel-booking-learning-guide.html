02 / Business framing

Start with a decision, not a model

A cancellation affects planning. A hotel may hold a room for someone who later cancels, while demand from other guests changes. An operations team needs visibility into likely cancellations, but it must also avoid treating reliable guests unfairly.

Three different questions

QuestionKind of workWhat it can tell you
Which groups canceled more often in the historical data?Descriptive analysisPast patterns and group comparisons.
How likely is this booking to cancel?Predictive modelingAn estimated probability, subject to validation.
Will sending a reminder prevent cancellation?Causal evaluationRequires an experiment or an appropriate causal design; SQL and a risk model alone cannot answer it.
Practical scenario: a model flags a booking as higher risk. A sensible next step might be a low-cost confirmation reminder tested in a controlled pilot. It is not automatically a reason to cancel the guest's reservation, charge them more, or overbook the hotel.

Define when the prediction is made

Write a sentence such as: "Estimate cancellation risk using information available when the booking is first created." This sentence determines which columns are allowed. A detail learned after the booking was made cannot be used to simulate a booking-time prediction.

Alternatively, predicting a week before arrival is a different product with different allowable features. Do not mix the two silently.

Turn the problem into a project question

"How do booking characteristics relate to cancellation, and can an interpretable model identify higher-risk bookings in a later time period?"

Try it: a segment has a higher cancellation rate and often uses a particular channel. Can you conclude that the channel causes cancellations?
Show the explanation

No. That channel may attract bookings made much further in advance, different customer types, or different hotels. Those differences can explain part of the pattern. You can report an association and propose a test, not claim causation.

03 / Read the data like a booking

A row represents one booking record, not necessarily one guest, one night, or one unique person. A column stores an attribute. Your analysis must keep that unit of measurement consistent.

05 / Phase 1

Setup and data quality: make the denominator trustworthy

Cleaning is not "delete anything unusual." It is a series of documented decisions about meaning, validity, and scope. Preserve the source and build a clean analytical layer separately.

Step 1: Load without hiding parsing problems

The importer reads your local CSV into PostgreSQL using text columns first. This preserves unexpected values for inspection before typed cleaning. Reading a raw table successfully is not the same as validating it.

# PowerShell, from the project folder after configuring .env:
.\.venv\Scripts\python.exe -m src.load_data

# Then inspect the schema with DBeaver.

Python uses COPY FROM STDIN, so the PostgreSQL server does not need access to a Windows file path on your machine. Do not separately use DBeaver's import wizard: use the importer for consistent source record numbers, checksums, and quality auditing. See DATA.md for the exact null markers.

Step 2: Ask what missing really means

Example problemTempting mistakeBetter documented decision
children is blank.Always replace it with 0.Missing is unknown, not necessarily no children. Profile it, preserve a flag, and justify any imputation separately.
agent is blank.Delete the booking.Check whether this represents no agent or unknown agent. Retain the booking unless there is a justified exclusion.
country is missing.Guess it from hotel location.Keep it unknown; the guest's country is not the hotel's country.
is_canceled is not 0 or 1.Convert every unexpected value to 0.Flag the invalid label and exclude/quarantine it from labeled analysis under an explicit policy.

Step 3: Handle zero-guest records carefully

Fictional cleaning examples

A row with adults = 0, children = 0, and babies = 0 has no recorded guests. A row with adults = 0 and children = 2 does not have zero guests. A row with children missing has an unknown total, not a confirmed total of zero.

-- Assumes guest columns have already been validated and typed.
SELECT
    *,
    CASE
        WHEN adults IS NULL OR children IS NULL OR babies IS NULL
            THEN 'unknown_guest_count'
        WHEN adults = 0 AND children = 0 AND babies = 0
            THEN 'zero_guests'
        ELSE 'positive_guests'
    END AS guest_count_status
FROM hotel_booking.bookings_quality;

For a guest-booking analysis, confirmed zero-guest records may be excluded from the clean analytical table while remaining in raw data. Do not apply that exclusion before inspecting the records and documenting the choice.

Step 4: Construct and validate dates

Fictional date construction example

Year = 2017, month = July, day = 15 becomes a single arrival date: 2017-07-15. A constructed date such as February 31 is invalid.

-- Fictional PostgreSQL example with known valid pieces:
SELECT make_date(2017, 7, 15) AS arrival_date;

-- Review actual parse failures after running the importer:
SELECT source_record_number, exclusion_reasons
FROM hotel_booking.bookings_quality
WHERE 'invalid_arrival_date' = ANY(exclusion_reasons);

make_date constructs a calendar date. The actual cleaning SQL first maps English month names and uses a session-local safe wrapper: impossible dates become NULL with an explicit exclusion reason. It never silently normalizes February 31 into another date. Inspect the flagged raw values before approving the policy.

Step 5: Investigate duplicates and implausible values

Identical rows are not automatically duplicate bookings. Two different guests can make bookings with identical recorded attributes. Without a trusted identifier, preserve them by default or justify another policy; report any sensitivity analysis separately.

Negative lead times, negative guest counts, invalid labels, and failed numeric casts need flags. Very high room rates or zero-night stays deserve investigation, not arbitrary deletion. A rare value is not necessarily a wrong value.

06 / Phase 2

SQL analysis: ask one clear question at a time

Most cancellation queries share the same structure: select a population, group if needed, count bookings, count cancellations, and divide using that same population.

Cancellation rate = canceled bookings / all eligible bookings

Run the eight-booking example yourself

The following SQL is self-contained in a PostgreSQL session in DBeaver and creates only fictional teaching data. Its short hotel/deposit labels are simplified for readability. Temporary tables exist only in the connection that creates them.

DROP TABLE IF EXISTS pg_temp.toy_bookings;
CREATE TEMP TABLE toy_bookings AS
SELECT * FROM (VALUES
    ('A', 'City',   10, 'Direct',    'None',       1, 1, 0),
    ('B', 'City',  120, 'TA/TO',     'None',       0, 0, 1),
    ('C', 'Resort', 90, 'TA/TO',     'None',       0, 2, 0),
    ('D', 'Resort',  5, 'Direct',    'Nonrefund',  0, 0, 0),
    ('E', 'City',  200, 'TA/TO',     'None',       0, 0, 1),
    ('F', 'City',   40, 'Corporate', 'None',       1, 0, 0),
    ('G', 'Resort', 60, 'Direct',    'Refundable', 0, 1, 1),
    ('H', 'Resort', 15, 'TA/TO',     'None',       0, 0, 0)
) AS t(
    booking_id, hotel, lead_time, channel, deposit,
    repeat_guest, requests, is_canceled
);

-- Question: What share of eligible bookings canceled overall?
SELECT
    count(*) AS bookings,
    sum(is_canceled) AS cancellations,
    avg(is_canceled::numeric) AS cancellation_rate
FROM toy_bookings;

The fictional output is bookings = 8, cancellations = 3, rate = 0.375. A dashboard can format 0.375 as 37.5%; do not multiply by 100 twice.

Read the calculation line by line

  • count(*) counts rows: your booking denominator.
  • sum(is_canceled) adds the ones: the cancellation numerator.
  • avg(is_canceled::numeric) averages a validated binary outcome, giving the same rate.
  • FROM identifies the exact population being analyzed.

Important: SQL averages ignore NULL. If the target contains NULL, the rate denominator can differ from count(*). Validate the target first and explain any exclusion.

Compare hotel types

-- Question: How does cancellation rate differ by hotel type?
SELECT
    hotel,
    count(*) AS bookings,
    sum(is_canceled) AS cancellations,
    avg(is_canceled::numeric) AS cancellation_rate
FROM toy_bookings
GROUP BY hotel
ORDER BY hotel;

Fictional answer

City has 2 cancellations among 4 bookings: 50%. Resort has 1 among 4: 25%. The overall rate is 3/8 = 37.5%. These tiny groups are a teaching device, not evidence about real hotel performance.

Turn a numeric field into meaningful bands

-- Question: How does cancellation rate vary by lead-time band?
WITH banded AS (
    SELECT
        CASE
            WHEN lead_time < 30 THEN '01: under 30 days'
            WHEN lead_time < 90 THEN '02: 30-89 days'
            ELSE '03: 90+ days'
        END AS lead_time_band,
        is_canceled
    FROM toy_bookings
)
SELECT
    lead_time_band,
    count(*) AS bookings,
    sum(is_canceled) AS cancellations,
    avg(is_canceled::numeric) AS cancellation_rate
FROM banded
GROUP BY lead_time_band
ORDER BY lead_time_band;

CASE creates the labels; WITH names an intermediate result. The bands are illustrative choices, not discovered optimum thresholds. Invalid or missing lead times must be handled before this query, or explicitly placed in an Unknown group.

No. These fictional groups have different sizes. Combine their counts: 91 / 102 = approximately 89.2%, not 70%. Use a weighted calculation or recompute from underlying bookings.

07 / Phase 3

Segmentation: turn many rows into understandable groups

A segment is a defined group of bookings. It is not automatically a risk prediction. The best starting point here is a small rule set a nontechnical operations colleague can explain.

Use ordered rules so each booking belongs once

The following rules use every requested behavior: lead time, channel, deposit, repeat status, and requests. Rules are applied top to bottom; the first matching rule wins.

-- Question: What are the sizes and rates of behavior segments?
WITH segmented AS (
    SELECT
        *,
        CASE
            WHEN repeat_guest = 1
                THEN 'Returning guest'
            WHEN lead_time >= 90
                 AND channel = 'TA/TO'
                 AND deposit = 'None'
                THEN 'Advance agency, no deposit'
            WHEN requests >= 1
                THEN 'Other with requests'
            ELSE 'Other bookings'
        END AS segment
    FROM toy_bookings
)
SELECT
    segment,
    count(*) AS bookings,
    sum(is_canceled) AS cancellations,
    avg(is_canceled::numeric) AS cancellation_rate
FROM segmented
GROUP BY segment
ORDER BY bookings DESC, segment;
Fictional segment results from the eight-booking teaching table.
SegmentMembersSizeCanceledRate
Returning guestA, F200%
Advance agency, no depositB, C, E3266.7% rounded
Other with requestsG11100%
Other bookingsD, H200%

Notice that A has a request but belongs to Returning guest. C has requests but belongs to Advance agency, no deposit. This is intentional precedence, not an error. Change the order and you change the segment definitions.

Do not overread small groups. G's segment has a fictional 100% rate because it contains only one booking. That does not make it a reliable high-risk category. Always show sizes and consider uncertainty or minimum reporting sizes.

Why not clustering immediately?

Clustering discovers groups based on a similarity definition. That introduces choices about scaling, encoding, distance, and number of clusters. Your prompt deliberately starts with rules so the first version stays understandable. Add clustering only after you explicitly request it.

For later predictive use: define rules and thresholds using business reasoning or earlier training data. Do not inspect final test outcomes, redesign segments around them, and then claim an independent test.

Try it: a returning guest books 150 days in advance through TA/TO with no deposit. Where do they belong in these rules?
Show the answer

Returning guest, because that rule appears first. If you want overlapping segments instead, that is a different design: totals may exceed the number of bookings and must be labeled accordingly.

Stop and review: approve rule order, thresholds, missing-value handling, group sizes, and the difference between descriptive groups and individual predictions.

08 / Phase 4

A cancellation model without cheating

A model learns relationships from historical features and known outcomes. For a new booking, it produces a cancellation probability. That probability is an estimate, not a guarantee or a judgment about the guest.

Features and target

Features are inputs, such as lead time and channel. The target is the value being predicted: is_canceled. Never include the target itself among the inputs.

Why logistic regression first?

Logistic regression combines numeric inputs and encoded categories into a score and converts it to a probability between zero and one. It is a strong baseline because it is relatively simple to explain and inspect.

Fictional interpretation example

If a fitted feature has an odds ratio of 1.5, it is associated with 1.5 times the cancellation odds for the stated feature change, holding the other modeled inputs fixed. That does not mean a 50-percentage-point increase in probability, and it does not establish cause. Feature scaling and category reference levels must be stated when explaining coefficients.

A shallow decision tree can be the one tree-based comparator. It learns branching rules and may capture interactions logistic regression misses, but can overfit. Compare on the same features and chronological evaluation population.

Important dataset limitation: scheduled arrival date is not booking creation date. If you split by arrival date, describe it as a later-arrival holdout, not a perfect booking-time backtest. Long-lead future-arrival bookings may have been created before earlier-arrival bookings. A derived booking date (arrival date minus lead time) is only a proxy whose semantics need validation.

Label availability also matters: when simulating a historical deployment, training outcomes must already have been known at that cutoff. A booking created before the cutoff but resolved later is not a usable labeled example at that moment. Outcome dates can inform a carefully documented audit without being model features. If this dataset cannot support a faithful as-of reconstruction, state that limitation explicitly.

Fit preprocessing on training data only

Suppose missing lead time is replaced by a median. Calculate that median from the training set only. Learning it from all records lets future data influence the model. The same rule applies to scaling, category encoding, feature selection, and any learned calibration step.

The following illustrative code assumes train, validation, and test are already cleaned, chronologically separated pandas frames returned from PostgreSQL, and that feature timing has been reviewed. The feature choice is a teaching example, not a timing certification. The actual runnable starter is src\model.py.

from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

numeric = ["lead_time", "is_repeated_guest"]
categorical = ["hotel", "distribution_channel", "deposit_type"]
features = numeric + categorical

preprocess = ColumnTransformer([
    ("numeric", Pipeline([
        ("impute", SimpleImputer(strategy="median")),
        ("scale", StandardScaler()),
    ]), numeric),
    ("category", Pipeline([
        ("impute", SimpleImputer(strategy="most_frequent")),
        ("encode", OneHotEncoder(handle_unknown="ignore")),
    ]), categorical),
])

model = Pipeline([
    ("preprocess", preprocess),
    ("classifier", LogisticRegression(max_iter=1000)),
])

# Only the training partition teaches the pipeline.
model.fit(train[features], train["is_canceled"])
validation_risk = model.predict_proba(validation[features])[:, 1]

# Choose settings and a threshold using earlier validation data.
# Freeze them before inspecting final test results.
test_risk = model.predict_proba(test[features])[:, 1]

Encoding turns categories into machine-readable indicator columns. Scaling puts numeric inputs on comparable scales. handle_unknown="ignore" allows a later unseen category, but you should still monitor and report category drift rather than treat it as irrelevant.

A fair comparison

Use a fresh preprocessing pipeline for a shallow decision tree, tune it on earlier validation data, and keep the final test untouched. Compare both models using the same final holdout. Include a simple baseline, such as the training cancellation rate assigned to every booking, so you know whether the extra complexity adds value.

Do not repeatedly adjust the model after seeing final test scores. If you do, that period becomes development data and a new independent test period is needed.

Stop and review: approve the prediction moment, feature availability, date semantics, label-availability limitations, baseline, split, and final test report before producing dashboard risk summaries.

09 / Model evaluation in plain English

What the scores actually mean

Precision and recall depend on a threshold: the risk level at which you flag a booking. ROC-AUC evaluates ranking across thresholds. Calibration checks whether probabilities are believable. None of these alone tells you whether an intervention helps the business.

Start with a confusion matrix

Fictional test set of 20 bookings - separate from the eight-booking SQL example

Actually canceledActually not canceled
Flagged as likely to cancel6 true positives (TP)2 false positives (FP)
Not flagged3 false negatives (FN)9 true negatives (TN)

Precision: among the 8 flagged bookings, 6 canceled. Precision = 6 / (6 + 2) = 75%. This helps describe how many alerts are correct.

Recall: among the 9 actual cancellations, the model caught 6. Recall = 6 / (6 + 3) = 66.7% rounded. This describes how many cancellations were detected.

False positives create unnecessary outreach. False negatives miss opportunities to act. A lower threshold generally flags more bookings and often raises recall at the cost of precision, but inspect the actual validation tradeoff.

Try your own fictional counts

These inputs are a learning calculator, not a trained model.

ROC-AUC: can the model rank risk?

Imagine taking one canceled booking and one non-canceled booking. Does the model give the canceled one the higher score? ROC-AUC summarizes this ranking ability, counting a tied pair as half correct.

Fictional ranking example

Canceled bookings have risks 0.9 and 0.6. Non-canceled bookings have risks 0.7 and 0.2. There are four cross-outcome pairs. The model ranks three correctly: 0.9 beats both non-canceled scores, and 0.6 beats 0.2 but not 0.7. AUC = 3 / 4 = 0.75.

A constant-risk baseline has AUC 0.5 when both classes are present. AUC 1.0 is perfect ranking. AUC is not accuracy, not the percentage of cancellations prevented, and not a calibration score. AUC is undefined when the evaluated set contains only one outcome class.

Calibration: can you trust a probability?

Fictional calibration example

Suppose 10 bookings each receive a predicted risk of 0.8, but only 4 cancel. Their mean predicted risk is 80%, while the observed rate is 40%. The model is overconfident in this group. A model can rank cases well and still give misleading probabilities.

For a calibration check, group final test predictions into risk bins and report each bin's count, average predicted risk, and observed cancellation rate. Small bins have substantial uncertainty. If you later fit a probability calibrator, fit it using earlier data, not the final test.

What final test evaluation code looks like

This example continues the variables from the modeling chapter. The threshold is illustrative; it must be selected and frozen using earlier validation data.

import pandas as pd
from sklearn.calibration import calibration_curve
from sklearn.metrics import (
    precision_score, recall_score, roc_auc_score,
)

y_test = test["is_canceled"]
threshold = 0.50  # Illustrative; select before final test evaluation.
test_flag = test_risk >= threshold

if y_test.nunique() != 2:
    raise ValueError("Final test data must contain both outcome classes.")
if not test_flag.any():
    raise ValueError("No test alerts; precision is undefined. Report this.")

scores = {
    "precision": precision_score(y_test, test_flag),
    "recall": recall_score(y_test, test_flag),
    "roc_auc": roc_auc_score(y_test, test_risk),
}
observed, predicted = calibration_curve(
    y_test, test_risk, n_bins=5, strategy="quantile"
)

# Group counts should also accompany the calibration display.
test_predictions = pd.DataFrame({
    "actual": y_test.to_numpy(),
    "risk": test_risk,
})

Quantile bins aim for similar group sizes; identical risk values can reduce the number of nonempty bins. Preserve the realized bin definitions and counts. Do not replace undefined metrics with a flattering number or silently tune against the test set.

Why not report only accuracy?

Fictional imbalance example

If only 10 out of 100 bookings cancel, a model that says "not canceled" for everyone has 90% accuracy and catches no cancellations. High accuracy can coexist with zero operational usefulness.

Try it: which metric matters if the team can afford only a small number of reminder calls, and which matters if missing cancellations is especially costly?
Show the explanation

Precision is particularly relevant to limiting wasted calls, while recall describes cancellations missed. In practice, choose a threshold using earlier validation data, team capacity, intervention cost, and benefit assumptions. A useful additional capacity metric is precision among the top-ranked bookings, but it does not replace the required metrics.

Calculate a trend in PostgreSQL

-- Question: How do cancellation rates vary by arrival month and hotel?
SELECT
        date_trunc('month', arrival_date)::DATE AS arrival_month,
        hotel,
        count(*) AS bookings,
        sum(is_canceled) AS cancellations,
        avg(is_canceled::numeric) AS cancellation_rate
    FROM hotel_booking.bookings_clean
    GROUP BY arrival_month, hotel
    ORDER BY arrival_month, hotel;

The actual export command runs this kind of PostgreSQL query and writes the returned rows locally with Python. You do not need PostgreSQL server-side filesystem permissions. The month is the scheduled stay month, not the month someone clicked Cancel. A cancellation-event timeline needs a separate, carefully defined query using outcome timing.

Common dashboard mistakes

  • Summing rates: use total cancellations / total bookings for the filtered population. Do not sum percentages or average differently sized groups without weights.
  • Joining incompatible grains: joining one row per segment onto one row per month can multiply rows. Keep separate fact tables or design a proper model.
  • Showing mixed populations: historical SQL totals may cover all clean records, while risk scores cover only the later test period. Label those populations visibly.
  • Hiding zero-booking months: if adding a calendar to show gaps, use zero counts but leave cancellation rate undefined when the denominator is zero.
  • Calling risk a certainty: a high-risk band still includes bookings that do not cancel.

Store rates as decimals between 0 and 1 and format them as percentages in the visualization. Document bin boundaries, segment rules, refresh date, and source population. Export aggregate data rather than unnecessary record-level details.

12 / Throughout the project

Small engineering habits that make analysis credible

Type hints: make intent visible

"""Validate booking labels before computing cancellation summaries."""

def cancellation_rate(labels: list[int]) -> float:
    if not labels:
        raise ValueError("At least one booking is required.")
    if any(label not in (0, 1) for label in labels):
        raise ValueError("Cancellation labels must be 0 or 1.")
    return sum(labels) / len(labels)

list[int] describes the expected input; -> float describes the output. Type hints aid readers and tooling but do not validate data automatically. The checks explicitly reject invalid inputs instead of returning a misleading zero.

This tiny function is for learning Python and tests; the project's main cancellation aggregations still belong in SQL. The opening docstring explains why the module exists, not merely "this file contains functions."

pytest: turn assumptions into checks

import pytest
from src.quality import cancellation_rate

def test_known_fictional_example() -> None:
    assert cancellation_rate([0, 1, 0, 1]) == pytest.approx(0.5)

def test_invalid_label_is_rejected() -> None:
    with pytest.raises(ValueError, match="0 or 1"):
        cancellation_rate([0, 2])

def test_empty_population_is_rejected() -> None:
    with pytest.raises(ValueError, match="At least one"):
        cancellation_rate([])

These examples assume the function has been saved in src\quality.py. They illustrate tests; that module is not created by this guide.

What actual data-quality tests should cover

  • Required columns exist and conversions are audited.
  • The analytical target is non-null and binary.
  • Retained records obey approved guest-count and date rules.
  • Confirmed zero guests are excluded if that policy was approved.
  • Raw, retained, and excluded populations reconcile without double counting.
  • Each booking receives exactly one segment under exclusive rules.
  • Training, validation, and test periods are ordered and disjoint.
  • Known leakage columns are not model features.
  • Exported cancellation counts never exceed their booking counts.

A test that passes does not prove all data are correct. It proves that the specific assertion holds for the tested input. Test the cleaning transformations as well as the final table: a bad cleaning rule can produce a neat-looking table.

Dependencies and reproducibility

A requirements file should describe the tested Python packages. Record the Python version, dataset source/version or file checksum, execution order, output locations, and any random seed used by the comparator. A seed helps reproduce stochastic behavior; it does not fix a bad split.

Small commits

A commit is a focused saved change in Git. Useful commit subjects might be "Add raw import and schema audit," "Document zero-guest policy," or "Add cancellation queries by channel." Avoid one giant commit that hides every decision. Never commit secrets, local environments, or raw data by accident.

What a phase handoff should contain

State what changed, where the outputs are, which assumptions need approval, and any known limitations. Then stop. "Work in phases" is a collaboration rule, not just a set of section headings.

13 / Connect the pieces

Follow one booking all the way through

Fictional booking B from our teaching table

1. Raw record

B is a City booking, made 120 days ahead, through TA/TO, with no deposit, no repeat-guest flag, no special requests, and a cancellation outcome of 1.

2. Quality layer

Before B enters the analysis, validate its label, guest fields, numeric fields, and constructed arrival date. Retain or exclude it according to the agreed policies, not because its outcome is inconvenient.

3. SQL summaries

B contributes one booking and one cancellation to the overall rate, the City group, the TA/TO channel, and the appropriate lead-time band. Groupings answer different questions; adding all those group totals together would count the same booking several times.

4. Behavior segment

B is not a repeat guest. It then satisfies the advance-agency/no-deposit rule and joins B, C, and E. That segment's fictional rate is 2/3, but it is not automatically B's individual model probability.

5. Model input

If B falls in the final test period, the model sees only its audited, allowable features. It must not see B's cancellation label or final status when predicting. Its actual outcome is used afterward to evaluate the prediction.

6. Risk score

Suppose, purely for explanation, B receives a risk of 0.72. This does not mean it will "72% cancel" as a single event. It means the model estimates a 72% probability; among many comparably scored bookings, calibration asks whether the observed frequency is similar.

7. Dashboard

B contributes to the historical arrival-month summary. If scored as part of the final test, it also contributes to the corresponding test risk bin. The dashboard should not imply those two files cover identical populations.

8. Business action

An operations team could consider a reminder pilot for a defined population. Before claiming value, define the intervention, cost, success measure, guest safeguards, and comparison group. Model evaluation alone cannot establish that the reminder works.

The whole chain: business decision → raw records → documented clean population → SQL patterns → understandable groups → leakage-aware prediction → honest evaluation → dashboard evidence → a testable business recommendation.

Earlier arrivals train the model; the middle period selects thresholds; later arrivals form the final test. Each partition must have both outcomes. This is not a random split. The acknowledgment makes the final-extract timing limitation explicit; it does not certify a booking-time snapshot.

A later-arrival holdout is not a booking-time backtest. Booking creation order can differ from arrival order. The scaffold does not reconstruct these histories and is not deployment validation.

Both models explicitly exclude final status and status date, use an allowlist, and fit preprocessing only on training. Logistic regression is the prespecified primary; one shallow tree is the comparator. A constant training-rate baseline provides context.

Each model's threshold is chosen using earlier validation F1 on a fixed grid from 0.1 to 0.9, with deterministic tie-breaking. This is a transparent teaching default, not a cost- or capacity-optimized operations policy. No threshold is selected from final test outcomes.
